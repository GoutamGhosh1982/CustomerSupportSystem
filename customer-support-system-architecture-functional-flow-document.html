1 · System Overview

The Customer Support Ticketing System is a full-stack microservices application that enables customers to raise support tickets and allows support agents to triage, respond to, and resolve them in real time. The system is decomposed into six independently deployable services that communicate over HTTP (REST) and asynchronously via RabbitMQ.

StakeholderRoleKey Capabilities
CustomerTicket submitterSubmit tickets · Track own ticket list · Reply in thread · View status updates
AgentSupport staffView all tickets · Reply · Update status · See internal notes
SupervisorTeam leadAll Agent capabilities + Assign tickets + View analytics
AdminSystem administratorAll capabilities + Manage users + Change roles + Deactivate accounts

2 · High-Level Architecture

Database-per-Service pattern: Each microservice owns its own SQL Server database. No service ever queries another service's database directly — cross-service data flows only through RabbitMQ events or REST API calls via the Gateway.

3 · Service Breakdown

🚪 API Gateway
localhost:5000 · YARP
  • Single entry-point for React SPA
  • Route-based reverse proxy to all services
  • JWT token validation before forwarding
  • CORS policy enforcement
  • WebSocket pass-through for SignalR
No database
👤 User Service
localhost:5004 · UserDB
  • Register new accounts (Customer default)
  • Login with BCrypt password verification
  • Issue JWT tokens (8 hr expiry)
  • List / get users (Agent+)
  • Change user role (Supervisor+)
  • Deactivate user accounts (Supervisor+)
  • Seed users re-hashed on every startup (ensures credentials always valid)
Table: Users
🎫 Ticket Service
localhost:5001 · TicketDB
  • Create ticket with auto-generated number
  • Calculate SLA deadline by priority
  • Enforce state machine (Open→InProgress→Escalated→Closed)
  • Paginated / filtered ticket listing
  • Assign ticket to agent
  • Publish events to RabbitMQ
Table: Tickets
💬 Response Service
localhost:5002 · ResponseDB
  • Add customer or agent reply to ticket thread

  • Publish response.added event

🔔 Notification Service
localhost:5003 · NotificationDB
  • Consume all domain events from RabbitMQ
  • Send email via SMTP on ticket events
  • Push real-time notifications via SignalR hub
  • Broadcast to role groups (agents) or ticket groups
  • Log every delivery attempt to DB

⚛️ React Frontend
localhost:3000 · Vite + TS
  • Login / Register pages (Zod validation)
  • Submit ticket form (customer)
  • My Tickets list (customer)

  • Analytics dashboard (charts + KPIs)
  • Admin user management
  • Real-time updates via SignalR hook

TicketDB — Tickets Table

ColumnTypeConstraintDescription
IdUNIQUEIDENTIFIERPKAuto GUID
TicketNumberNVARCHAR(20)UNIQUEHuman-readable (TKT-0001)
TitleNVARCHAR(200)NOT NULLShort issue summary
DescriptionNVARCHAR(MAX)NOT NULLFull problem description
StatusNVARCHAR(20)CHECK (Open|InProgress|Escalated|Closed)Current lifecycle state
PriorityNVARCHAR(10)CHECK (Low|Medium|High|Critical)Urgency level → drives SLA
CategoryNVARCHAR(50)NOT NULLIssue type classification
CustomerIdUNIQUEIDENTIFIERNOT NULLFK to UserDB.Users.Id (logical)
AssignedToIdUNIQUEIDENTIFIERNULLAgent GUID when assigned
SlaDeadlineDATETIME2NULLCritical=4h, High=8h, Medium=24h, Low=48h
CreatedAt / UpdatedAt / ClosedAtDATETIME2—Lifecycle timestamps
SQL Server Trigger note: The Tickets table has a database-level trigger. EF Core's default UPDATE statement uses an OUTPUT clause which SQL Server forbids on triggered tables. The EF Core model is configured with t.UseSqlOutputClause(false) in TicketDbContext.OnModelCreating() to use a compatible UPDATE form.

6 · Functional Flows — UI to DB

6.1 — User Login

1
React — LoginPage.tsx User enters email + password. React Hook Form + Zod validates fields client-side. On submit calls authApi.login() → POST /api/auth/login via Axios.
2
Gateway — YARP Receives request on :5000. Matches /api/auth route. No JWT check on auth routes. Forwards to UserService :5004.
3
UserService — AuthController.Login() Looks up user by email via UserRepository.GetByEmailAsync(). Runs BCrypt.Verify(password, hash). Checks IsActive == true.
4
UserDB — SQL Query SELECT * FROM Users WHERE Email = @email. Returns User row with PasswordHash, Role, FullName.
5
UserService — AuthService.GenerateToken() Creates JWT with claims: userId, email, fullName, role. Signed with HMAC-SHA256. Expires in 8 hours.
6
React — authStore (Zustand) Receives AuthResponse (token, userId, fullName, email, role). Stores in localStorage. Zustand state updated → isAuthenticated = true. Redirects: Customer → /tickets, Agent+ → /dashboard.

6.2 — Customer Creates a Ticket

1
React — SubmitTicketPage.tsx Customer fills Title, Description (min 20 chars), Category, Priority. Zod schema validates. useCreateTicket() mutation calls POST /api/tickets with JWT Bearer header.
2
Gateway — YARP Validates JWT token (signature, expiry, issuer). Extracts claims. Forwards to TicketService :5001 with all headers intact.
3
TicketService — TicketsController.Create() Checks [Authorize(Roles="Customer")]. Reads userId, fullName, email from JWT claims. Calls TicketAppService.CreateAsync().
4
TicketService — TicketAppService.CreateAsync() Queries GetCountAsync() → generates TKT-{n:D4} number. Calculates SLA: Critical=4h, High=8h, Medium=24h, Low=48h. Builds Ticket entity. Calls TicketRepository.CreateAsync().
5
TicketDB — SQL INSERT EF Core executes: INSERT INTO Tickets (Id, TicketNumber, Title, Description, Status, Priority, Category, CustomerId, SlaDeadline, ...) VALUES (...). Status defaults to Open.
6
TicketService → RabbitMQ Publishes TicketCreatedEvent to exchange support.events with routing key ticket.created. (Non-fatal: if RabbitMQ unavailable, ticket is still saved.)
7
NotificationService — TicketEventConsumer Consumes notif.ticket.created queue. Calls EmailService.SendAsync() to customer. Calls SignalR hub → broadcasts TicketCreated event to agents group.
8
React — useSignalR hook Agent dashboards listening on SignalR receive TicketCreated event. TanStack Query cache invalidated → dashboard auto-refreshes without page reload. Toast notification shown.
9
React — SubmitTicketPage.tsx Receives 201 Created + TicketDto. Shows success toast with ticket number. Navigates to /tickets/{id} (TicketDetailPage).

6.3 — Agent Views Dashboard

1
React — AgentDashboard.tsx Component mounts. useTickets(filters) hook fires. TanStack Query checks cache (staleTime 30s). On cache miss → calls GET /api/tickets?status=&priority=&page=1&pageSize=20.
2
Gateway → TicketService JWT validated (role must be Agent/Supervisor/Admin). Forwarded to :5001.
3
TicketService — TicketRepository.GetAllAsync() Builds dynamic LINQ query: WHERE Status = @s AND Priority = @p AND Category = @c. Executes COUNT for total. Applies ORDER BY CreatedAt DESC, SKIP/TAKE for pagination.
4
TicketDB — SQL Two queries: SELECT COUNT(*) FROM Tickets WHERE ... and SELECT ... OFFSET n ROWS FETCH NEXT 20 ROWS ONLY. Returns PagedResult<TicketDto>.
5
React — AgentDashboard.tsx Renders table with StatusBadge + PriorityBadge components. Filter dropdowns bound to state → onChange triggers new query with updated params. Pagination controls update page number.

6.4 — Agent Updates Ticket Status

1
React — TicketDetailPage.tsx Agent clicks "Mark as Closed" button. useUpdateTicketStatus() mutation fires: PATCH /api/tickets/{id}/status body: {"status":"Closed","note":"Issue resolved"}.
2
TicketService — UpdateStatusAsync() Loads ticket from DB. Validates new status is in ["Open","InProgress","Escalated","Closed"]. Records old status. Sets ticket.Status = "Closed", ticket.ClosedAt = UtcNow. Saves via EF Core (UseSqlOutputClause(false) ensures compatibility with the Tickets table trigger).
3
TicketDB — SQL UPDATE EF Core executes UPDATE Tickets SET Status='Closed', ClosedAt=@now, UpdatedAt=@now WHERE Id=@id without an OUTPUT clause (required due to SQL trigger on the table).
4
RabbitMQ — ticket.updated event Publishes TicketUpdatedEvent with oldStatus, newStatus, updatedBy, note. Wrapped in try/catch — if RabbitMQ is unavailable the DB update is still committed and a [WARN] is logged. Notification service consumes → pushes TicketUpdated to SignalR group ticket-{id}.
5
React — real-time refresh All browsers viewing that ticket receive SignalR push. TanStack Query cache for ["ticket", id] is invalidated → refetch → UI updates status badge instantly without page reload.

6.5 — Agent/Customer Adds a Response

1
React — TicketDetailPage.tsx User types reply in text area. Agents can tick "Internal note" checkbox. On submit: useAddResponse() calls POST /api/responses body: {"ticketId":"...","body":"...","isInternal":false}.
2
ResponseService — ResponsesController.Add() Reads userId, fullName, email, role from JWT claims. Sets authorType = role == "Customer" ? "Customer" : "Agent". Calls ResponseAppService.AddAsync().
3
ResponseDB — SQL INSERT INSERT INTO Responses (Id, TicketId, AuthorId, AuthorType, Body, IsInternal, CreatedAt) VALUES (...).
4
RabbitMQ — response.added event ResponseAddedEvent published. NotificationService consumes → broadcasts ResponseAdded to SignalR group ticket-{ticketId}.
5
React — thread refresh SignalR event received. useResponses(ticketId) query invalidated → refetch. New bubble appears in thread. Customers only see IsInternal = false responses; agents see all.

6.6 — Real-time Notification Pipeline

1
Any Service → RabbitMQ Ticket or Response service publishes event to topic exchange support.events with a routing key (ticket.created, ticket.updated, ticket.assigned, response.added).
2
RabbitMQ — queue routing Exchange routes to bound durable queues: notif.ticket.created, notif.ticket.updated, notif.ticket.assigned, notif.response.added. Message persisted until consumed.
3
NotificationService — TicketEventConsumer BackgroundService with AsyncEventingBasicConsumer. Deserialises JSON payload. Dispatches to appropriate handler (HandleTicketCreated, HandleTicketUpdated, etc.).
4
Email via SMTP For ticket.created and ticket.assigned: calls SmtpEmailService.SendAsync(). Sends HTML email. Delivery result logged to NotificationLogs table.
5
SignalR push to React IHubContext<NotificationHub> used to push to groups: agents group (new tickets/assignments) or ticket-{id} group (status updates, responses). Message delivered to all connected browser tabs in that group.
6
React — useSignalR hook HubConnection registered in Layout.tsx (always-on). Handlers call queryClient.invalidateQueries() to trigger refetch + toast.info() for visual alert. No polling — purely event-driven.

7 · RabbitMQ Event Bus

Routing KeyPublished ByQueueConsumed ByAction
ticket.createdTicketServicenotif.ticket.createdNotificationSvcEmail to customer + SignalR to agents
ticket.updatedTicketServicenotif.ticket.updatedNotificationSvcSignalR to ticket-{id} group
ticket.assignedTicketServicenotif.ticket.assignedNotificationSvcEmail to agent + SignalR to agents group
response.addedResponseServicenotif.response.addedNotificationSvcSignalR to ticket-{id} group
Resilience: All Publish() calls in TicketAppService (CreateAsync, UpdateStatusAsync, AssignAsync) and ResponseAppService are individually wrapped in try/catch. If RabbitMQ is unavailable the HTTP operation succeeds and the DB change is committed — a [WARN] is written to the console. RabbitMQ is an optional enhancement, not a hard dependency for core CRUD operations.

v2.1 Changelog
  • Bug fix — ticket status update (500 error): The Tickets table has a SQL Server trigger. EF Core's UPDATE was using an OUTPUT clause which SQL Server forbids on triggered tables. Fixed by adding t.UseSqlOutputClause(false) to TicketDbContext.
  • Bug fix — RabbitMQ resilience in UpdateStatusAsync / AssignAsync: Publish() calls in these two methods were not wrapped in try/catch (unlike CreateAsync). When RabbitMQ is offline, both methods now catch and log the error instead of propagating a 500 to the client.
  • Bug fix — seed user passwords: DbSeeder.UpsertUser() previously skipped overwriting the hash if a BCrypt hash already existed (even if it was a placeholder for an unknown password). The condition now always overwrites, ensuring seed credentials (Admin@123, Agent@123, Customer@123) are always valid after startup.
  • New launcher script: Launch-CustomerSupport.ps1 — single Admin PowerShell script that installs Erlang/RabbitMQ if missing, builds the solution, runs npm install, launches all 6 service windows, and opens the browser.
