Detailed RabbitMQ and SignalR Communication Architecture

This document describes how the Customer Support System microservices communicate through RabbitMQ and SignalR, how messages flow between producers and consumers, what each event contains, and how asynchronous backend events are delivered to users through email and real-time updates.

Executive summary

The system uses HTTP through the Gateway for request-response operations, RabbitMQ for asynchronous service-to-service event propagation, and SignalR for real-time browser updates. TicketService and ResponseService publish integration events. NotificationService consumes those events, logs them, sends email where applicable, and broadcasts live updates to frontend clients through SignalR hubs.

Exchange: support.events SignalR hub: /hubs/notifications Queues: notif.* Topic routing Real-time push

1. Services participating in communication

Gateway

Public entry point for API and hub traffic. Routes HTTP calls and the notifications hub connection.

UserService

Supports authentication and users. It is not directly participating in the RabbitMQ event chain documented here.

TicketService

Stores ticket data and publishes ticket lifecycle events after create, update, and assignment operations.

ResponseService

Stores ticket responses and attachments, then publishes response-related events.

NotificationService

Consumes events from RabbitMQ, persists notification logs, sends emails, and broadcasts real-time SignalR events.

SharedKernel

Provides event contracts, RabbitMQ settings, publisher abstractions, and connection helpers shared across services.

2. Communication model

Synchronous path

Frontend calls enter through the Gateway and are routed to domain services such as TicketService and ResponseService.

Asynchronous path

After data is persisted, producer services publish events to RabbitMQ. NotificationService consumes those events and performs notification side effects independently of the originating HTTP request.

Real-time path

NotificationService exposes a SignalR hub and broadcasts selected event results to live frontend connections. This is how agents and ticket viewers receive instant UI updates without polling.

5. SignalR component

Hub endpoint

NotificationService exposes the SignalR hub at /hubs/notifications. The Gateway forwards hub traffic to NotificationService.

Broadcast groups

Live events are broadcast to named groups including agents and ticket-scoped groups such as ticket-{TicketId}.

  • TicketCreated is broadcast to the agents group.
  • TicketAssigned is broadcast to the agents group.
  • TicketUpdated is broadcast to a ticket-specific group.
  • ResponseAdded is broadcast to a ticket-specific group.

6. Producers and published events

Ticket creation

Routing key: ticket.created

Contains ticket identity, title, priority, category, customer information, and timestamp.

Ticket update

Routing key: ticket.updated

Contains old and new status, updater information, note, and timestamp.

Ticket assignment

Routing key: ticket.assigned

Contains agent and customer details with assignment timestamp.

Response creation

Routing key: response.added

Contains response id, ticket id, author information, message body, internal flag, and creation timestamp. The current publisher leaves TicketNumber empty.

7. End-to-end data flows

Flow A: Ticket created

  1. Frontend submits a ticket through the Gateway.
  2. TicketService saves the ticket and publishes ticket.created.
  3. RabbitMQ routes the event to notif.ticket.created.
  4. NotificationService consumes it, emails the customer, stores a notification log, and sends a SignalR TicketCreated update to the agents group.

Flow B: Ticket updated

  1. Frontend updates ticket status through the Gateway.
  2. TicketService persists the new status and publishes ticket.updated.
  3. RabbitMQ routes the event to notif.ticket.updated.
  4. NotificationService records an in-app notification and sends a SignalR TicketUpdated event to the relevant ticket group.

Flow C: Ticket assigned

  1. Frontend submits assignment through the Gateway.
  2. TicketService updates assignment data and publishes ticket.assigned.
  3. RabbitMQ routes the event to notif.ticket.assigned.
  4. NotificationService emails the assigned agent, stores a log entry, and broadcasts SignalR TicketAssigned to the agents group.

Flow D: Response added

  1. Frontend submits a response through the Gateway.
  2. ResponseService stores the response and publishes response.added.
  3. RabbitMQ routes the event to notif.response.added.
  4. NotificationService logs the event and broadcasts SignalR ResponseAdded to the relevant ticket group.

8. Delivery, acknowledgement, and failure behavior

Publisher behavior

TicketService and ResponseService use a fallback strategy. If RabbitMQ is unavailable when the service starts, they can continue business operations using a no-op publisher.

Consumer behavior

NotificationService uses manual ack and nack handling. Failures are negatively acknowledged without requeue, so retries are not automatic in the current setup.

9. Final assessment

This architecture combines synchronous API routing, asynchronous event-driven messaging, and real-time SignalR broadcasting in a way that fits a customer support platform well. RabbitMQ decouples notification work from transactional ticket and response operations, while SignalR ensures that agents and customers can see changes immediately in the UI.

The strongest next-step improvements would be dead-letter queue support, retry strategy, and stronger atomicity guarantees between database writes and event publication.
